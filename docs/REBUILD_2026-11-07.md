## 1. Décodeur SPL qui préserve le mint

`dmaga/spl.py` décode chaque instruction System et SPL, internes comprises. Un compte de jetons est rapporté à son propriétaire et à son mint, dans l'ordre :
1. par les soldes pre/post de la transaction ;
2. par les `initializeAccount*` de la même transaction, pour un compte créé puis fermé dans la transaction.

Règles :
- les montants restent des entiers bruts ;
- une transaction échouée ne produit aucun mouvement ;
- un compte non résolu garde `owner_known=False`.

Fixtures réelles (`tests/fixtures/spl/`, `tests/test_spl_decoder.py`) :

| Cas | Résultat attendu |
|---|---|
| `Transfer` sans le compte du mint (6t2dz4jm → AtZj) | mint et propriétaires retrouvés |
| `TransferChecked` (7GVC → 9Sxm) | même décodage |
| compte WSOL créé et fermé dans la transaction (vente de 9Sxm) | propriétaire retrouvé par l'initialisation |
| ATA WSOL fermée (clôture Perps de 7GVC) | solde courant rendu |
| transaction échouée | aucun mouvement |

Le rejeu historique (`investigations/2026-11-06_historical_replay/scripts/h_decode.py`) utilise désormais ce module.

### Contrôle complémentaire du 7 novembre : clôture WSOL temporaire

Le décodeur suit désormais explicitement les transferts natifs System et les lamports de `createAccount` pendant l'exécution de la transaction, avant d'évaluer `closeAccount`. Sans cela, un compte WSOL créé, alimenté et fermé dans une seule transaction pouvait restituer un montant inférieur au remboursement réel du **loyer du compte**.

Régression déterministe : reçu `2PHU4HTS…` (9Sxm, 15 juillet 2024), `2 039 280` lamports de création + `17 874 608 396` lamports reçus en WSOL − `211 782 429` transférés en WSOL = **`17 664 865 247` lamports remboursés** lors du `closeAccount`. Le test `test_transient_wsol_close_refunds_creation_rent` vérifie ce résultat avec le reçu brut figé. Cela ne change pas la jambe de swap déjà identifiée (`17.874608396 SOL`).

## 8. Correctif après fusion : une arête n'est ajoutée que si sa transaction est absente de `trades`

### Erreur démontrée
- La règle d'ajout (`dmaga/positions.py`, recopiée dans `ana_20_pnl.py`) réinjectait une arête `gtba` dès qu'aucun de ses deux bouts n'avait de ligne dans `trades` pour cette signature.
- 701 arêtes (49,431 M) remplissaient cette condition alors que leur transaction était déjà lue dans `trades`. Ce sont des jambes de passage d'une route (réserve → routeur → acheteur), sur 696 transactions du 21/07/2024 au 02/11/2026.
- Relues dans le brut par `scripts/chk_23_netting_raw.py` : les deux bouts sont à net DMAGA nul, ou une venue, pour 701 arêtes sur 701 (liste : `reports/data_checks/passthrough_edges.csv`, signature, chemin d'instruction, nets). `parse_tx` avait déjà écrit le net de chaque propriétaire : les réinjecter les comptait deux fois.
- Exemple figé, `YQMWMCwa…` (11/11/2025), route WSOL → USDC → USDT → DMAGA :
  - instruction `o4.11` : réserve `4F6uLJwk…` → routeur `ARu4n5mF…`, 8 453 336,089924 jetons ;
  - instruction `o4.13` : routeur → `Bya5eBy9…`, même montant ;
  - `trades` n'a qu'une ligne, le swap de `Bya5eBy9…` ; l'ancienne règle donnait 8,45 M fantômes au routeur.
- L'échantillon du §2 contenait une de ces arêtes (`5F3QVQM2…`, la seule où le mint est cité). Il l'a jugée conforme parce qu'il ne vérifiait que l'existence du mouvement.

### Correction
- Une seule règle, dans `dmaga/positions.py` : une arête n'est ajoutée que si sa transaction est absente de `trades` (22 152 arêtes, 2 126,3 M). `ana_20_pnl.py` l'importe au lieu de la recopier ; `ana_61`, `ana_64` et `chk_22` l'utilisaient déjà.
- `chk_22` sépare désormais « aucune jambe, transaction absente » et « aucune jambe, transaction lue ».
- Tests :
  - `tests/test_positions.py` : route réserve → routeur → acheteur dans une transaction lue ; échoue avec l'ancienne règle (routeur +8 M, réserve −8 M), passe avec la nouvelle ;
  - `tests/test_spl_decoder.py` : la transaction réelle `YQMWMCwa…` donne les deux mouvements DMAGA et `parse_tx` n'écrit que le net de l'acheteur.

### Hypothèse inverse : un virement réel ignoré parce que le propriétaire a une autre ligne dans `trades`
- **Non établi, aucun cas trouvé.** Sur les 35 676 arêtes `gtba` dont la transaction est dans `trades` (31 750 transactions, toutes retrouvées dans le brut) : 0 mouvement absent, 0 bout absent de `trades` à net non nul. Pour 83 245 couples (transaction, propriétaire hors venue), le net de `trades` égale le net brut (`reports/data_checks/netting_raw.json`).
- Cas réels couverts : 27 682 transactions à plusieurs mouvements DMAGA, 17 469 avec fermeture de compte (WSOL temporaires compris), 386 avec une instruction Token-2022. Les soldes DMAGA relèvent du programme Token classique (`programId` des soldes) et un mint n'appartient qu'à un programme : ces instructions Token-2022 portent sur d'autres jetons.
- Limite : les 22 152 transactions absentes de `trades` ne sont pas dans le brut local. Leur ajout repose sur l'API de transferts, relue sur le RPC public pour 39 d'entre elles (échantillon du §2).
